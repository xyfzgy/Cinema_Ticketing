# 影院售票系统功能清单与实现步骤

本文对应当前仓库：后端在 `springboot/`，前端在 `vue/`，Java 包名为 `com.gaoyu.springboot`。粘贴的目录清单使用 `backend/`、`frontend/` 和 `com.example.cinema`，阅读时分别映射到现有位置，不要再建第二套包或入口类。

当前大多数 Java 文件只是空类或空接口；新增的 XML、提示词也只是骨架。以下是**待实现功能**，不是已完成功能。每完成一个模块，按“数据库及规则 → Entity/DTO → Mapper → Service → Controller → 后端测试 → 前端 API/页面 → 联调”的顺序推进。

## 0. 开工前统一约定

1. 保留现有 `SpringbootApplication.java` 作为唯一启动入口。检查 Java 21、Maven、Node，并运行 `mvn -q -DskipTests package` 确认基线可编译。
2. 先整理 `springboot/pom.xml`：只保留当前阶段实际需要的依赖，后续引入 Redis、RabbitMQ、AI、支付时再加对应 starter。若继续使用 Spring Security，明确写安全配置；若采用原文档的 JWT 自定义拦截器方案，避免 Security 默认规则把公开接口挡住。
3. 改 `springboot/src/main/resources/application.yml`：当前默认指向旧库 `movie_db`，有写死的数据库/Redis 密码，MyBatis XML 路径也与现有 `resources/mapper/*.xml` 不一致。改为独立的 `cinema_dev`，敏感值从环境变量读取；测试使用 `cinema_test`。先只保留确实启用的配置。
4. 写 `database/init.sql`、`database/dev-data.sql` 前先统一命名：订单实体已有 `TicketOrder`，Mapper 同时有 `OrderMapper` 和 `TicketOrderMapper`；`PayStatus` 与 `PaymentStatus`、`SeatStatus` 与 `ScreeningSeatStatus`、`IdempotencyUtil` 与 `IdempotencyUtils`、两组 `mq/Order*Producer/Consumer` 也有重叠。每组保留明确的一套或划清职责，避免同一业务状态出现两个来源。
5. 所有接口统一以 `/api` 开头；普通用户身份只取认证上下文。时间统一规定时区，金额在 Java 使用 `BigDecimal`、数据库使用 `DECIMAL(10,2)`。状态更新使用条件更新或事务保护，不依赖前端状态。
6. 每个功能至少验证成功、参数错误、无权限和重复请求；涉及座位、支付、消息的功能还要验证并发与重试。测试不是只运行现有的 `contextLoads()`。

## 第一阶段：基础工程与账号

### 1. 健康检查和统一响应

**文件：**`SpringbootApplication.java`、`common/Result.java`、`PageResult.java`、`ErrorCode.java`、`BusinessException.java`、`GlobalExceptionHandler.java`；可在 `controller/` 新建 `HealthController.java`。

1. 定义成功响应 `{code, message, data}`；分页结构包含总数、页码、每页数量和列表。错误码至少区分参数错误、未登录、无权限、资源不存在、业务冲突和服务器错误。
2. 全局异常处理分别接住参数校验异常、业务异常和未知异常。未知异常记日志，响应中不要暴露堆栈。
3. 加 `GET /api/health`，返回简单的运行状态。先启动服务访问它，再逐步接数据库；健康接口不应依赖尚未实现的业务逻辑。
4. 写 Web 层测试：成功响应字段正确，非法参数有清晰错误，未知异常不会向用户泄露内部信息。

**完成标准：**服务能启动，健康接口可访问，响应和错误格式一致。

### 2. 数据库基础和开发数据

**文件：**`database/init.sql`、`database/dev-data.sql`、`database/README.md`，各 `entity/`、`mapper/` 文件，`config/MybatisPlusConfig.java`。

1. 第一批建 `sys_user`、`movie`、`cinema`、`hall`、`seat`、`screening`、`screening_seat`、`ticket_order`、`order_item`；明确主键、外键或逻辑关联、创建/更新时间及索引。
2. 唯一约束至少包括用户名、订单号、`(hall_id,row_no,col_no)`、`(screening_id,seat_id)`。订单号、幂等键、支付流水号分别设置适当唯一约束。
3. 各 `Entity` 字段与真实表一致；枚举约定数据库保存的值；Mapper 先实现简单 CRUD，复杂查询再放到 XML。确认 `@MapperScan` 或 `@Mapper` 生效。
4. `dev-data.sql` 只放少量电影、影院、影厅和测试账号。账号密码用实际采用的加密器生成哈希，不能写明文密码到表中。
5. 在全新 `cinema_dev` 执行脚本，验证可重复从空库部署；用独立 `cinema_test` 做集成测试，不对旧库执行清理。

**完成标准：**空库能按 README 顺序建表并导入数据，基础 Mapper 能正确读写。

### 3. 注册、登录、退出和权限

**文件：**`entity/User.java`、`dto/LoginRequest.java`、`RegisterRequest.java`、`vo/LoginVO.java`、`UserVO.java`、`enums/UserRole.java`、`UserStatus.java`、`mapper/UserMapper.java`、`service/AuthService.java`、`service/impl/AuthServiceImpl.java`、`service/UserService.java`、`controller/AuthController.java`、`utils/PasswordUtils.java`、`JwtUtils.java`、`CurrentUserUtils.java`、`interceptor/JwtInterceptor.java`、`LoginUserContext.java`、`config/WebConfig.java`。

1. 注册 DTO 校验用户名、密码等；Service 检查用户名唯一，强制新用户为普通角色，使用 BCrypt 存储密码。
2. 登录按用户名查用户，校验账号状态和密码，签发有有效期的 JWT；`LoginVO` 仅返回令牌和必要用户信息，绝不返回密码哈希。
3. 拦截器验证签名、到期时间、用户是否有效，并把用户 ID/角色放入请求上下文；请求完成后清理上下文。公开放行登录、注册、健康接口和允许匿名浏览的接口。
4. 管理接口校验管理员角色；个人数据接口再按用户 ID 校验归属。退出与令牌撤销在基础流程后补齐；若使用无状态 JWT，第一版退出仅清理前端令牌，后续再引入服务端撤销/刷新机制。
5. 前端在 `vue/src/api/auth.js`、`stores/user.js`、`views/auth/`、`router/` 实现表单、持有令牌和路由守卫。
6. 测试重复用户名、错误密码、停用用户、过期或伪造令牌、普通用户调用管理员接口。

**完成标准：**能注册、登录，普通用户不能越权，所有个人接口从令牌识别用户。

## 第二阶段：电影、影院与排片

### 4. 电影管理和用户浏览

**文件：**`entity/Movie.java`、`dto/MovieQuery.java`、`MovieCreateRequest.java`、`MovieUpdateRequest.java`、`vo/MovieVO.java`、`enums/MovieStatus.java`、`mapper/MovieMapper.java`、`service/MovieService.java`、`service/impl/MovieServiceImpl.java`、`controller/MovieController.java`、`controller/admin/AdminMovieController.java`。

1. 定字段：片名、简介、片长、类型、海报地址、上映日期、上下架状态等；确定哪些字段必填及长度限制。
2. 管理端实现新增、编辑、上下架和分页筛选；用户端只查上架电影的列表与详情。分页和搜索条件在 Service 中统一处理。
3. 若接海报上传，校验文件大小、格式及路径，保存后返回可访问地址；不要信任用户提供的本地文件路径。
4. 前端写 `api/movie.js`、`MovieList.vue`、`MovieDetail.vue`、`MovieManage.vue` 和 `MovieCard.vue`。
5. 测试：新增后可浏览；下架电影不会作为新购票入口；普通用户不能修改电影。

**完成标准：**管理员维护电影，用户能分页查找并查看详情。

### 5. 影院和影厅管理

**文件：**`entity/Cinema.java`、`Hall.java`、`dto/CinemaCreateRequest.java`、`HallCreateRequest.java`、`vo/CinemaVO.java`、`HallVO.java`、`mapper/CinemaMapper.java`、`HallMapper.java`、`service/CinemaService.java`、`HallService.java`、`controller/CinemaController.java`、`HallController.java`、`controller/admin/AdminCinemaController.java`、`AdminHallController.java`。

1. 影院记录名称、地址、营业状态；影厅归属于影院，记录名称、规模与状态。
2. 管理端实现影院、影厅的新增、编辑、启停和列表；用户端仅展示可营业的影院/影厅相关场次。
3. 删除或停用前检查是否有关联的未来场次及订单；有交易记录时优先停用，不做物理删除。
4. 前端写 `api/cinema.js`、`CinemaManage.vue`、`HallManage.vue`；电影详情页可按影院过滤场次。

**完成标准：**影厅始终归属有效影院，已有交易不因误删而失去关联。

### 6. 固定座位和座位图

**文件：**`entity/Seat.java`、`dto/SeatCreateRequest.java`、`vo/SeatVO.java`、`enums/SeatType.java`、`mapper/SeatMapper.java`、`service/SeatService.java`、`controller/SeatController.java`、`controller/admin/AdminSeatController.java`；前端 `SeatMap.vue`、`SeatManage.vue`。

1. 固定座位保存影厅 ID、排号、列号、座位类型、是否可用；数据库用 `(hall_id,row_no,col_no)` 防重复。
2. 管理端按行列生成座位，支持标记过道、损坏或不可售座位。前端座位图按行列稳定渲染，区分可选、占用、已售、不可售。
3. 有未来场次或历史订单的影厅，禁止直接重建座位编号；需要变更时先定义迁移规则。
4. 测试重复坐标、跨影厅座位以及不可售座位下单。

**完成标准：**影厅座位布局稳定，不能售出停用座位。

### 7. 排片和场次座位

**文件：**`entity/Screening.java`、`ScreeningSeat.java`、`dto/ScreeningCreateRequest.java`、`ScreeningUpdateRequest.java`、`vo/ScreeningVO.java`、`ScreeningSeatVO.java`、`enums/ScreeningStatus.java`、`ScreeningSeatStatus.java`、`mapper/ScreeningMapper.java`、`ScreeningSeatMapper.java`、`resources/mapper/ScreeningMapper.xml`、`service/ScreeningService.java`、`service/impl/ScreeningServiceImpl.java`、`controller/ScreeningController.java`、`controller/admin/AdminScreeningController.java`。

1. 管理员选择上架电影、可用影厅、开始时间和票价；后端根据电影时长计算结束时间，并考虑清场间隔。
2. 在事务中锁定影厅或采用等效串行化策略，检查同影厅时间区间不重叠；不能只在前端检查。
3. 创建场次时，同事务根据固定座位初始化 `screening_seat`；停用座位按规则标记不可售。任一步失败都回滚。
4. 用户可按电影、影院、日期查询场次及座位。已有订单的场次限制改时间、影厅和删除。
5. 前端写 `api/screening.js`、`ScreeningList.vue`、`ScreeningManage.vue`、`ScreeningCard.vue`。
6. 测试边界时间、清场间隔、并发创建冲突场次和场次座位数量。

**完成标准：**重叠排片被拒绝，所有可售场次有完整座位快照。

## 第三阶段：下单、支付与票券

### 8. 选座和创建订单

**文件：**`entity/TicketOrder.java`、`OrderItem.java`、`dto/CreateOrderRequest.java`、`vo/OrderVO.java`、`OrderDetailVO.java`、`enums/OrderStatus.java`、`mapper/OrderMapper.java` 或 `TicketOrderMapper.java`、`OrderItemMapper.java`、`resources/mapper/OrderMapper.xml`、`service/OrderService.java`、`service/impl/OrderServiceImpl.java`、`controller/OrderController.java`、`utils/OrderNoGenerator.java`、`IdempotencyUtil.java` 或 `IdempotencyUtils.java`。

1. 下单请求只传场次、座位 ID 和幂等键；用户 ID 来自登录上下文，金额由服务器根据场次票价计算。
2. 校验场次未开场、座位属于该场次、数量在限制内、无重复座位、所有座位仍可售。
3. 在一个事务中创建待支付订单及明细，按固定顺序对每个场次座位做“仅当可选时改为占用”的条件更新；任一失败回滚全部。
4. 为订单设置过期时间和唯一订单号。同一用户重复提交同一幂等键及参数，返回同一订单；同键不同参数报冲突。
5. 前端写 `SeatSelect.vue`、`OrderConfirm.vue`、`api/order.js`、`stores/order.js`。
6. 测试双人抢同座、多座位其中一个被抢、重复提交、伪造金额、未登录下单。

**完成标准：**同场同座只能产生一个有效占用，失败订单不留下部分占座。

### 9. 订单查询、取消和超时关闭

**文件：**`OrderService`、`OrderController`、`scheduler/OrderExpireScheduler.java`、`controller/admin/AdminOrderController.java`；前端 `OrderList.vue`、`OrderDetail.vue`、`OrderManage.vue`。

1. “我的订单”按登录用户分页查询，订单详情同时查明细及座位；管理员可按状态、时间、订单号筛选。
2. 用户只能取消自己的待支付订单。事务中先条件更新订单状态为已关闭，再只释放归属该订单的占用座位。
3. 定时扫描过期的待支付订单，复用同一个关闭逻辑。支付和关闭都按“订单 → 座位”顺序加锁或条件更新，让竞争只有一方成功。
4. 测试越权查询、重复取消、到期与支付同时发生、关闭后座位重新可售。

**完成标准：**订单状态和座位状态始终一致，超时可自动释放。

### 10. 开发环境模拟支付

**文件：**`dto/MockPayRequest.java`、`entity/Payment.java`、`enums/PaymentStatus.java`、`service/PaymentService.java`、`service/impl/PaymentServiceImpl.java`、`controller/PaymentController.java`；前端 `Payment.vue`、`PaymentResult.vue`。

1. 模拟支付接口仅在开发/演示环境开放；生产配置必须禁用它。
2. 服务端检查订单归属、待支付状态和到期时间。事务中条件更新订单为已支付，再把该订单占用的座位改为已售，并记录模拟支付流水。
3. 重复支付返回已完成结果或明确冲突，不能重复记账或重复出票。订单已关闭时支付必须失败。
4. 测试重复请求、错误用户、超时订单、支付与超时关闭竞争。

**完成标准：**能从注册、浏览、选座、下单一路操作到支付成功。

### 11. 票券查询与验票

**文件：**`entity/Ticket.java`、`vo/TicketVO.java`、`enums/TicketStatus.java`、`mapper/TicketMapper.java`、`service/TicketService.java`、`controller/TicketController.java`；前端 `TicketList.vue`、`TicketCard.vue`。

1. 每个已支付订单明细生成一张票，票号或核验码唯一；关联订单、场次、座位和持有人。
2. 用户仅可查看自己的票，管理员或验票员按授权核验。验票更新必须为“仅未使用可核验”的条件更新。
3. 退款或取消后的票不能继续使用；同一票重复核验应给出明确结果。
4. 测试重复出票、越权查票、重复验票和退款后的票状态。

**完成标准：**支付后的票可查、可核验，重复操作不会生成第二张有效票。

## 第四阶段：缓存、消息与正式支付

### 12. Redis 缓存、锁和刷新令牌

**文件：**`config/RedisConfig.java`、`utils/IdempotencyUtil.java`、`service/AuthService.java` 及电影、座位相关 Service；前端 `api/request.js`、`stores/user.js`。

1. 先缓存电影列表/详情，定义键名和过期时间；电影修改事务提交后删除相关缓存。
2. 若增加短期锁座，锁值必须记录请求或订单归属；释放时原子核对归属。多座位只取得一部分锁时清理已取得的锁。
3. Redis 只用于加速和短期协调，最终是否可卖仍以数据库场次座位的条件更新为准。
4. 实现刷新令牌轮换和退出撤销，刷新失败让前端重新登录；不同环境使用不同 Redis 键前缀。
5. 测试缓存失效、锁过期、误释放保护、Redis 暂停后的售票一致性。

**完成标准：**缓存内容不会长期过时，Redis 故障不会造成重复售票。

### 13. RabbitMQ 可靠出票

**文件：**`config/RabbitMqConfig.java`、`entity/OutboxEvent.java`、`mapper/OutboxEventMapper.java`、`mq/OrderPaidEvent.java`、`OrderClosedEvent.java`、生产者和消费者、`scheduler/OutboxRetryScheduler.java`。

1. 先声明交换机、队列、绑定、死信队列，并验证一条测试消息可发送和消费。
2. 支付数据库事务同时写 `outbox_event`。提交后由投递任务发送消息，收到确认后标记已发送；失败按次数重试。
3. 消费者按订单明细或业务唯一键幂等出票；数据库事务提交后再确认消息。处理失败重试，超过上限进入死信队列并记录人工补偿信息。
4. 前端在支付成功后区分“出票中”和“已出票”；不能因为队列暂时不可用就把已支付订单改回未支付。
5. 测试重复投递、消费者崩溃、RabbitMQ 中断后恢复、同一订单只产生一套票。

**完成标准：**消息可重试且不重复出票，队列中断后能补投。

### 14. 支付渠道沙箱、回调和退款

**文件：**`entity/Payment.java`、`Refund.java`、`dto/PaymentRequest.java`、`PaymentCallbackRequest.java`、`RefundRequest.java`、`vo/PaymentVO.java`、`enums/PaymentStatus.java`、`RefundStatus.java`、`mapper/PaymentMapper.java`、`RefundMapper.java`、`resources/mapper/PaymentMapper.xml`、`service/PaymentService.java`、`RefundService.java`、`controller/PaymentController.java`、`RefundController.java`。

1. 先选定支付沙箱并阅读其官方接口文档，记录商户号、密钥、订单号和回调验签规则；密钥只放环境变量或本地秘密配置。
2. 后端生成支付请求，保存本地支付单及渠道流水。前端只接收支付链接/参数，不自行决定金额。
3. 回调先验签，再核对商户、订单、金额和渠道状态；按唯一流水和状态条件更新幂等入账。网络超时通过主动查询渠道补偿，不能盲目再次扣款。
4. 退款先创建申请，调用沙箱后依据渠道确认结果改变退款与票券状态。已关闭订单的迟到支付回调进入核对/退款流程，不能重新占用座位。
5. 真实环境禁用模拟支付。测试伪造回调、重复回调、迟到回调、退款重试和部分失败。

**完成标准：**沙箱付款与退款可追踪、可核对，重复通知不重复入账。

## 第五阶段：用户中心、后台与 AI

### 15. 用户中心

**文件：**`service/UserService.java`、`vo/UserVO.java`、订单/票券/退款的查询接口；前端 `Profile.vue`、`OrderList.vue`、`TicketList.vue`。

1. 提供查看与修改个人资料、修改密码、查看自己的订单/票券/退款进度。
2. 敏感操作要求重新校验密码或身份；所有个人数据查询都从登录上下文获取用户 ID，绝不信任 URL 或请求体中的用户 ID。
3. 管理员可启停账号，停用后禁止新登录；历史交易记录继续保留。
4. 测试跨用户查询、跨用户修改、停用账号和密码更新。

**完成标准：**用户能管理自己的资料和交易记录，不能读写他人数据。

### 16. 运营后台与统计

**文件：**`controller/admin/*`、`vo/StatisticsVO.java`、`resources/mapper/StatisticsMapper.xml`；前端 `layouts/AdminLayout.vue`、`views/admin/*`、`api/admin.js`、`PageTable.vue`。

1. 后台统一做管理员权限校验，再接电影、影院、影厅、座位、排片、订单和支付管理页面。
2. 明确定义销售额、实收额、退款额、售出票数和上座率的统计口径；例如是否计入已退款订单、统计时间按支付时间还是场次时间。
3. 根据口径编写聚合 SQL，支持日期和影院筛选；管理端展示数字、趋势或表格，同时可下钻到订单明细核对。
4. 测试普通用户越权、退款后的统计变化、空时间段和跨日场次。

**完成标准：**管理员可维护资源并用订单明细核对统计数字。

### 17. AI 客服和推荐

**文件：**`config/AiConfig.java`、`ai/AiChatService.java`、`MovieRecommendTool.java`、`ScreeningQueryTool.java`、`service/AiService.java`、`controller/AiController.java`、`resources/prompts/customer-service.txt`；前端 `views/ai/CustomerService.vue`。

1. 等基础购票流程稳定后配置模型密钥，先实现纯文本问答；为请求设置超时、限流和清晰的失败响应。
2. 提示词写购票、退票规则及回答边界。推荐和场次查询工具只读数据库真实数据，不让模型编造影片或余座。
3. 聊天会话按用户隔离。查询订单时从认证上下文拿用户 ID，不能信任模型传入的身份；AI 不直接执行支付、退款或改订单。
4. 测试模型不可用、越权提问、工具返回空结果和并发聊天；AI 故障不影响普通购票。

**完成标准：**客服能回答规则并基于真实电影/场次推荐，不能读取他人订单。

## 第六阶段：前端体验、测试与交付

### 18. 前端公共能力与完整页面

**文件：**`vue/src/api/request.js`、各业务 API、`router/index.js`、`stores/`、`layouts/`、`views/`、`components/`、`directives/permission.js`、`styles/`、`utils/`。

1. `request.js` 统一设置 API 基地址、令牌、超时和错误提示；401 清理登录态，403 显示无权限，409 显示业务冲突。
2. 路由区分匿名页、用户页和管理员页；路由守卫改善体验，真正权限仍由后端校验。
3. 先做登录、电影列表/详情、场次、座位图、订单确认、支付结果、我的订单/票券；再做管理页和 AI 页。
4. 每页提供加载、空数据、错误和提交中状态；提交按钮防连点，但后端仍保留幂等保护。
5. 用 `npm run build` 验证构建，再在浏览器按完整购票流程联调。

**完成标准：**用户不用直接调用接口即可完成购票，管理员可完成日常维护。

### 19. 测试、迁移和部署

**文件：**`cinema`、`database/`、`docs/`、`deploy/`、根目录与后端 README。

1. 为 Service 写规则测试，为 Controller 写权限和参数测试，为数据库操作写集成测试；重点覆盖抢座、重复下单、支付与关单竞争、重复回调、重复消息。
2. 筛选旧项目需要的图片和影片资料，编写迁移脚本并在测试库核对。旧账号密码只有确认哈希兼容时才迁移；不要直接迁移旧订单到新交易表。
3. 写清环境变量、数据库初始化/升级顺序、启动命令和接口示例；提供不含真实密钥的配置示例。部署配置包含 MySQL、Redis、RabbitMQ 和前后端服务。
4. 使用独立生产数据库和密钥，启用 HTTPS、备份、日志与监控；正式切换前演练恢复，确认模拟支付接口已关闭。
5. 在全新环境按文档从零部署，完成“注册 → 登录 → 浏览 → 选座 → 下单 → 支付 → 查票”验收。

**完成标准：**新环境可复现部署、交易数据可恢复、旧项目仍保持完整。
